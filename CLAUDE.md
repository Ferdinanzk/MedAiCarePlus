# MedAiCarePlus — Claude Ground Rules

## What This Project Is
Full-stack medical care app (AIOT CAREBOX). React SPA served by FastAPI at port 8000.

Working features: face-recognition login (OpenVINO), emotion detection (ONNX), **live pill-intake monitoring** (the main feature — see below), medication tracking + intake scheduling, LINE notifications.

Prescription OCR (the Scan page) works for **every account** once `GEMINI_API_KEY` is in `.env` (a secret: never commit it; the repo is public). Nothing else is per installation or per account. See "Prescription OCR" below and `docs/OCR.md`. Without the key, OCR uses a local Ollama vision model if one answers, else `/health` reports `"ocr": false`. Ollama is used *only* by OCR; nothing else touches it.

## Repo Structure
```

  routers/          ← api_*.py = React JSON API; others = legacy Jinja2
    api_monitor.py  ← live intake monitoring endpoints
  services/         ← face_recognition, emotion, ocr, line, monitor, intake_detection

  dependencies.py   ← JWT auth (Supabase + face token)
  main.py           ← lifespan model warmup, routers, SPA serving
frontend_source/    ← React source (Vite + Tailwind) — THE ONLY frontend copy

```

There is **no `medaicareplus-web/` twin directory** and no manual file-sync step. The Dockerfile builds `frontend_source/` in a `node:22-alpine` stage and copies `dist/` → `/app/static/web`. Edit `frontend_source/` and rebuild.

## How to Run Locally
The running stack is **`docker-compose.yml`** (project `medcareai2`, services `postgres` + `app`):

```powershell
cd "d:\medcareai2_20260920\app"
docker compose up -d                 # start
docker compose up -d --build app     # rebuild after ANY backend or frontend edit
docker compose logs -f app           # tail logs
```

App: http://localhost:8080 · Health: http://localhost:8080/health. The host port is `WEB_PORT`, default 8080, because the Reachy Mini daemon owns 8000. The robot's device API is host port 8001, bound to `DEVICE_BIND`.

`docker-compose.dev.yml` is a *different* stack (services `medaicare` + `ollama` + `ngrok`) and is **not** what currently runs. Don't mix them.

## The Intake Monitor (main feature)

Pressing "take pill" opens a session that runs two **decoupled** HTTP streams concurrently:

1. **Landmark stream — ~15fps (66ms tick).** Browser Web Worker (`frontend_source/src/workers/monitorWorker.ts`) runs three MediaPipe models (face + hand + pose) and POSTs landmarks to `/api/intake/monitor/landmarks`. Server-side `PillIngestionDetector` (`services/intake_detection.py`) scores them — pure geometry/heuristics, **no neural net**.
2. **Vision stream — ≤5fps (200ms gate).** Uploads a ≤640×480 JPEG to `/api/intake/monitor/vision`, which runs OpenVINO face recognition (3 chained models) and the ONNX emotion model in a thread executor.

Session state lives in `services/monitor_service.py` (`MonitorRegistry`, in-memory, one session per user).

### Critical gotcha — detector thresholds are frame-rate-calibrated
`moving_toward()` (`intake_detection.py:93-96`) returns a **raw per-frame delta** with no division by elapsed time. So `APPROACH_SPEED_THRESHOLD_NORM` (0.05) and `ERRATIC_APPROACH_STD_NORM` (0.18) are implicitly tuned to ~15fps.

**Lowering the capture rate silently miscalibrates scoring** — it does not degrade gracefully. At ~3fps the deltas are ~5× larger, which loses `trajectory_contribution` (+0.12) and trips the erratic penalty (−0.05): a −0.17 swing against `CONFIRM_THRESHOLD = 0.40`, so genuine intakes stop auto-confirming with no error. Before changing fps, normalize `moving_toward()` by elapsed time and re-validate.

Practical floor is ~8fps. The frontend self-throttles (`tick()` returns early while `workerBusyRef`/`landmarkBusyRef` are set), so slow hardware reduces sample rate rather than queueing.

## Architecture Decisions (do not change without discussion)

### Auth — face tokens only
`get_current_user` (`app/dependencies.py`) accepts **only** face tokens: `itsdangerous.URLSafeTimedSerializer(SECRET_KEY)`, 8h expiry, stored as `face_auth_token` in localStorage, carrying `u_id`. Email/password login (`/api/auth/email-login`, bcrypt) also returns a face token. Supabase is **not used**: `frontend_source/src/lib/supabase.ts` is imported nowhere, and `/api/auth/link-account` still expects a Supabase `sub` claim, so it cannot work (pre-existing, left as-is).

### Consent is enforced server-side (Phase 1, terms version `2026-10`)
- Data routes depend on **`get_consented_user`**, not `get_current_user`. It returns 403 `consent_required` unless the user's latest `core` consent is granted at the current `TERMS_VERSION`. New authenticated routes must use it unless they belong to *limited mode*. `tests/test_consent_enforcement.py` introspects every route and fails on a missed swap.
- Limited-mode (exempt) routes: `/api/consent/*`, `/api/legal/*`, `/api/account/export`, `/api/account/delete`, `/api/auth/onboarding-status`, `GET /api/memory`, `DELETE /api/memory`, `DELETE /api/memory/fact`, plus the open login/register/identify/webhook routes. `tests/test_consent_enforcement.py` checks method + path for the memory routes (`POST`/`PATCH` on the same paths stay consent-gated).
- The legal notice text lives in `app/legal/<kind>/<version>/<lang>.json` (`core` now; `robot` for Reachy later), **not** in `i18n.ts`. `legal_service` renders operator fill-ins and hashes the canonical JSON. Consent rows reference `(kind, version, language, sha256)`. Changing the text means bumping `TERMS_VERSION`, which re-prompts everyone.
- Consent state is cached per process for 5 s and invalidated on write. It's append-only; the latest state is the highest `consent_id` per scope.
- Account deletion writes `deletion_ledger` plus a host JSONL (`./ledger`, mounted at `/ledger`). `scripts/restore.ps1` replays it after any restore; the app refuses to start while `ops_state.restore_in_progress` exists.
- The LINE webhook **always** requires a valid `X-Line-Signature`. With an empty `LINE_CHANNEL_SECRET`, every webhook call returns 401.
- `APP_ENV=prod` makes startup fail on the default `SECRET_KEY`, an empty LINE secret, empty legal fill-ins, or `LIVE_VOICE_TEST` on (`app/startup_checks.py`). With `REACHY_FEATURE_ENABLED` it also fails on an empty `RISK_CLASSIFIER_API_KEY`, and on an AI setup whose job models are `openrouter/free` or lack their company, region or retention (`check_ai_settings`). On the first start that check runs on `.env`'s values before anything is copied (`ai_store.seed_from_env`), so a refused first start copies nothing and fixing `.env` works; after that the settings are fixed on the AI connections card (start once with `REACHY_FEATURE_ENABLED=0` to reach it). `dev` (the default) only warns.

### Reachy robot (Phase 2): one process, two listeners
- `python -m app.serve` (the Dockerfile CMD) runs **two uvicorn servers in one process**, sharing one lifespan, one scheduler, and one in-memory `MonitorRegistry`: public `:8000`, plus device `:8001` for `/api/device/*`. Port 8001 is never published or tunnelled. The middleware in `main.py` returns 404 for device routes on 8000, 404 for anything else on 8001, and 401 for device tokens (`rdv1.` prefix) on 8000. WebSockets follow the same rule (Phase 2a): a WebSocket to `/api/device/*` on 8000, or to any other path on 8001, is refused, and a test walks every WebSocket route. `uvicorn app.main:app` alone gives you **no** device API.
- `reachy_bridge/` is the robot-side SDK (its own container, `docker compose --profile reachy up -d reachy-bridge`). It is a client of the device API only. It never decides a dose was taken; the server records under policy.
- The server enforces recording policy:
  - `MonitorSession` never auto-commits while `degraded` (< 12 fps, a gap > 0.25 s, or < 1 s of history), in `observe` mode, or when `auto_commit` is false.
  - Device sessions get `auto_commit = device.auto_record AND dose supported` (`dose_form='solid_oral' AND units_per_dose=1`).
  - `reachy_device.auto_record` **defaults to FALSE** until decision D2 (recording without pill identification) is made.
- Unverifiable doses go to `pending_confirmation`, and a caregiver answers with LINE buttons (a postback HMAC-signed with `SECRET_KEY`; the sender must be that verified contact). `transition_intake` refuses to change a `pending_confirmation` dose under the row lock. Confirmations expire after max(missed window, 2 h).
- **Every LINE push added from Phase 2 on goes through `notification_outbox`** (`app/services/outbox.py` to enqueue; `outbox_dispatcher` delivers with `X-Line-Retry-Key`). Don't call `LineService.send_*` directly for new notifications.
- Withdrawing `robot_camera` consent (or unpairing) calls `reachy_tasks.revoke_devices` in the same transaction.
- **The robot streams frames; the server computes the landmarks.** The robot's Pi 4 reached only ~3 fps running the six face/hand/pose models itself, below the 12 fps recording gate. `POST /api/device/monitor/frame` takes one JPEG plus its capture `timestamp` (seconds, robot clock). `LandmarkService` (`services/landmark_service.py`, code in `services/landmarks/`, ported from the robot app's `vision.py`) computes the packet and feeds `registry.landmarks`. Identity and emotion run on the same frames in the background every 0.5 s, or at once while a candidate waits. Each session keeps its own trackers (`MonitorSession.vision_engine`), and its frames are processed in order under `frame_lock`. Measured at about 29 ms per frame on this laptop.
- The six landmark ONNX files live in `models/landmarks/` and are committed, like the emotion model (`.gitignore` excludes `*.onnx` except these). They're pinned by SHA-256, and `/health` reports `"landmarks"`.
- The robot app can listen for the patient's "I finished" phrase with Whisper Base via faster-whisper on the robot, but only while the `robot_microphone` consent is current. The server sends `microphone` in the task payload and every heartbeat. It is a claim, not evidence: if the camera resolves nothing within 8 s, the robot files a `patient_claim` confirmation.
- The robot app's source is in `reachy_app/` (published as the Hugging Face space `pearlyjam21/medcare_reachy`: 0.7.0 since 12 Oct 2026; the space's history also holds an ElevenLabs voice line numbered 0.6.0, 4-5 Oct, that is on no GitHub branch and is not in 0.7.0). `reachy_app/tools/deploy_to_robot.py` copies it onto the robot. After deploying, restart the app through the daemon (`POST /api/apps/restart-current-app`): saving settings restarts only its worker thread, and the process keeps running the old code.
- **Voice clips** are WAVs rendered on the robot with Matcha (`~/.medcare_reachy/clips/zh-TW/`). The deploy renders a clip again when its zh-TW text in `bridge/clips/manifest.json` changed or its WAV is missing (`rendered.json` there records what each WAV says; the deploy writes it before uploading the new manifest, so a failed render is retried next time). The deploy fails when a planned clip was not written, and warns when Whisper does not hear a clip exactly as written. The voice reads Simplified Chinese, so a manifest edit also needs the clip's Simplified words in the tool's `SPOKEN` table; `reachy_app/tests/test_deploy_tool.py` fails until it has them.
- **The robot's camera tops out at 10 fps unless the daemon is changed.** Reachy Mini's daemon (reachy_mini 1.11) shares the camera with apps at `IPC_FPS = 10` (`/venvs/mini_daemon/.../reachy_mini/media/media_server.py`), whatever the app asks for. The stream then stays below the server's 12 fps, so every robot dose goes to family confirmation as `degraded` (seen 2 Oct 2026: `landmark_fps` 10.1 on every dose). **Deploying robot app 0.5.1 alone does not change that.** `deploy_to_robot.py --camera-ipc-fps 15` edits the constant and keeps a backup; it applies after a daemon restart, done by hand when no reminder is running. A daemon update undoes it. The stream rate and the daemon's and app's CPU at 15 fps have not been measured yet. The app's settings page shows "Camera feed" fps, and the app logs a warning when the camera stays below 12 fps.
- Robot app 0.5.1 streams in step with the camera rather than on a timer, and encodes each 1280x720 frame to 480x360 in one pass (~12 ms on the Pi, down from ~38 ms). Its speech listener runs at nice 5: decoding the patient's 「我吃完了」 coincided with the stream falling from 10 to 6-7 fps for ~3 s.
- **Stream stalls of ~1 s have an unknown cause.** On 2 Oct 2026 the robot's stream stopped for ~1 s at a time, then got 4-6 answers within 0.2 s. It happened in every slot state, mostly with the speech listener off, so it is not decoding. The robot's Wi-Fi power save is on (untested lead). A stall while WATCHING makes that dose `degraded` even at 15 fps. 0.5.1 logs each gap over 0.25 s (`server stream: ... between frames`, with the camera wait, event-loop lateness, and frames dropped behind unanswered requests). The server logs any frame it held up over 0.25 s (`monitor frame N of session ... took`).
- **Robot app 0.7.0: the camera watchdog** (`bridge/camera_watch.py`, `CameraWatchdog`). Before 0.7.0, a camera that stopped gave one stale frame and then `None` forever; the app logged nothing and searched for the full 10 minutes (`SEARCH_TIMEOUT`).
  - While a monitor session is attached, the stream (`MonitorStream.camera`, `bridge/runner.py`) calls the watchdog's `frame()` for every new frame and `tick()` when none came. Only a frame the SDK returns counts. A slow camera (5 fps) is not a stall: only a 2 s gap is.
  - **Stall:** no new frame for `CAMERA_STALL_SECONDS` (2 s). A stall is the start of an *episode*, which lasts until the camera has been healthy again (see Recovered). The app logs one ERROR line when an episode begins (`camera stalled: ...`), with the daemon's `GET /api/media/status` answer (`ReachyRobot.media_status()`); a further stall inside the same episode logs a WARNING (`camera stalled again`).
  - **Recovery**, at most once per `CAMERA_RECOVER_INTERVAL` (5 s) in a session: `ReachyRobot.reopen_camera()` asks the daemon for the media back when it says the media is released or unavailable (result `acquired`), else reopens the app's own camera reader (`reopened`). Either way the SDK builds the app's media link again, and that link also carries the speaker and the microphone: after a recovery on the real robot, check that Reachy still speaks and hears. A failed attempt (`failed: <reason>`) is logged and never stops the stream or the session.
  - **Speaker and microphone after a refused recovery:** a recovery releases the app's whole media link, so when the daemon then refuses to give it back, the speaker and the microphone are off too. `ReachyRobot.restore_media()` asks for it back (only the SDK's `acquire_media()`, never a release, under the playback lock the recovery uses; a no-op while the app has its media) at heartbeats and before a task wakes the robot, so the greeting can be heard. While the daemon keeps refusing it asks again at most once a minute (`RESTORE_RETRY_SECONDS`), because the SDK logs a WARNING and an ERROR for every refused acquire and each request can take 10 s. It never raises and logs one WARNING per streak of refusals. When the watchdog gives up while the media is still released, one ERROR says the speaker and microphone are off until the robot's media comes back.
  - **Recovered:** the first new frame after a stall shows the state `ok` again, and the slow-camera warning (below 12 fps) can fire again, counted from that frame. The episode ends only after `CAMERA_HEALTHY_SECONDS` (5 s) of frames with no gap of 2 s or more, and then one INFO line (`camera recovered`) gives the stall's length. A camera that gives one frame and stalls again (as it did after each recovery on 11 Oct 2026) stays in the same episode.
  - **Give up:** no steady frames `CAMERA_GIVE_UP_SECONDS` (15 s) after the episode's first stall gives the state `unavailable`. A search (`SEARCHING`) then ends as `not_found` with detail `{"reason": "camera_unavailable"}` (the not_found path also adds `outcomes`), and Reachy goes to sleep as for any `not_found`. `camera_unavailable` never records or skips a dose by itself: for a dose task the server's missed-dose path decides, as for any `not_found`. `unavailable` outlasts the search, so the heartbeats and the card keep reporting it, until the next session starts and tries the camera afresh.
  - The watchdog's log lines come from the logger `medcare_reachy.bridge.camera_watch`.
  - **Restarts:** `BridgeService.restart()` runs under `_restart_lock`, so two overlapping restarts (two quick Saves) never leave two bridge threads running, and the settings page disables Save and Restart while a request is pending.
- **The TCU companion takes the camera away.** TCU's Reachy AI Companion (the `reachy-mini-tcu` project, systemd unit `reachy-ai-companion`) connects with `media_backend="no_media"`. In reachy_mini 1.11.0 (`ReachyMini._configure_mediamanager`) such a connection makes the daemon release the camera and audio for direct use. Before 0.7.0 nothing asked for them back, so MedCare Reachy's camera reader (GStreamer `unixfdsrc`) stopped for good; from 0.7.0 the watchdog asks during a session, but the companion can release them again at any time. Don't run both: on our robot the companion is disabled at boot (`sudo systemctl disable --now reachy-ai-companion`). Both also serve their page on port 8042. On the robot, `curl -s localhost:8000/api/media/status` shows `"released": true` when a program took the media, and `curl -s -X POST localhost:8000/api/media/acquire` gives it back; during a session the 0.7.0 watchdog does that itself.
- **Finding the patient before a check-in: OpenVINO alone** (`monitor_service.openvino_only`). A robot session that *started* in `observe` mode for a **check-in task** (`reachy_task.reason = 'checkin'`, read at `/api/device/monitor/start` and kept as `MonitorSession.checkin_search`) verifies the patient with the OpenVINO match alone: exactly one face labelled as the patient, fewer than 4 OpenVINO faces (`saturated` false), a patient face at least 6.5% of the frame's width wide (`OPENVINO_ONLY_MIN_FACE_FRACTION`, about 32 px of 480x360; a smaller one is `searching`, not a hit), and 2 hits in a row whose boxes overlap by at least 0.20. It needs no MediaPipe face box on the same frame. Every other session keeps the full rule, which also needs a MediaPipe face overlapping the match by at least 0.20 and fewer than 4 MediaPipe faces: dose sessions, browser sessions, a dose session that switched to `observe` after recording, and the observe sessions of a dose task (the search before prompting a dose, the watch after it). `MonitorSession.started_mode` keeps the mode a session started in, because `mode` changes after a record. Why: the server's MediaPipe short-range face detector misses faces under about 50 px wide in the robot's 480x360 frame, so the robot could not verify a patient further than about 1.35 m, while dashboard login (OpenVINO alone) worked. Narrowed to check-in searches after the final review of 11 Oct: a dose task's search verified a patient 1.35-3 m away whom the strict dose session after it found `ambiguous`, so after 20 s the robot told that very patient 「我在等要吃藥的人，請他到我面前來。」 and stopped searching. The size floor replaces the one MediaPipe set by itself: without it, faces of about 24 px matched at distances of 0.20-0.27, close to the 0.3 threshold. A search session still never records a dose, and the dose prompt still waits for verification in that session. Since robot app 0.9.0 (companion session) a second kind of session uses this rule: an `observe` session that `/api/device/monitor/start` receives with `companion` true, because it never records and no dose prompt follows it (it keeps a companion chat's camera on, so the patient is recognised from across the room). The robot sends the flag only from the start of the chat, never on the search or the post-dose watch of a dose task.
  - **Identity log** (`_log_identity`): for robot sessions, one INFO line at every `identity_status` change, else at most one per 5 s per session: session id, status, rule (`openvino_only` or `with_mediapipe`), best patient distance, patient box width in pixels, and the OpenVINO and MediaPipe face counts. No images, and no labels other than patient/other.
- **Robot camera state on the Reachy card.** From robot app 0.7.0, every heartbeat carries `camera` (`CameraWatchdog.snapshot()`): `state` (`idle`, `ok`, `stalled`, `recovering` or `unavailable`), `fps`, `since` (when the state last changed) and `media` (the daemon's media status as read during the current stall, or null). `idle` means no session is attached, so 0 fps is normal then. The server validates it (`CameraReport` in `api_device.py`; an unknown state is a 422), stores it as `reachy_device.status_detail["camera"]`, and `/api/reachy/status` returns it as `camera`. The card shows "Robot camera not working" (「機器人鏡頭無法使用」) while the robot is online and the state is `stalled`, `recovering` or `unavailable`, and a "Robot camera" row whenever the state isn't `idle`: the camera fps while it is `ok`, and a dash (—) instead of a number while it is `stalled`, `recovering` or `unavailable` (the fps is a 10 s average that still counts the frames from before the stall). Robots older than 0.7.0 send no `camera`, and the card then shows nothing new. A task's `camera_unavailable` detail is stored with the task like any status detail.
- **Deploying robot app 0.7.0.** From `reachy_app/`: `python tools/deploy_to_robot.py --host <the robot's address>` (user `pollen`; the SSH password comes from `REACHY_SSH_PASSWORD`, or it asks). It backs up the installed app, uploads the package, installs faster-whisper and Whisper Base, and renders changed clips. On 11 Oct 2026 the robot ran 0.5.4 with an older SenseVoice `voice.py`; the upload replaces it with the repo's Whisper Base version. Then restart the app through the daemon, on the robot: `curl -s -X POST localhost:8000/api/apps/restart-current-app` (when the app isn't running: `curl -s -X POST localhost:8000/api/apps/start-app/medcare_reachy`). Heartbeats then report `bridge_version` 0.7.0. Robot checks: one real check-in (frames at the camera rate, the patient verified, the chat runs), then a camera failure: `curl -s -X POST localhost:8000/api/media/release` during a search must end in a recovery, or in `camera_unavailable` about 17 s after the last frame (2 s to notice the stall, then 15 s) with the camera warning on the card.

- **Two ways a robot can see.**
  - **Server vision** (robot app 0.4.0 default, `vision_on_server=true`): the robot streams frames to `/monitor/frame` and the server computes landmarks *and* emotion (`MonitorSession.vision_engine` is set).
  - **On-robot vision** (`vision_on_server=false`, and `reachy_bridge/`): the robot app runs the landmark models (MediaPipe models converted to ONNX, on ONNX Runtime; the MediaPipe library can't load on the robot's Pi 4) **and the emotion model**. That session's JPEGs (≤ 2 fps) are identity-only: `vision()` skips `EmotionService` for reachy sessions *without* a `vision_engine`. Emotion arrives as an optional `emotion: {face_index, probabilities}` on `/api/device/monitor/landmarks` and is accepted only for the verified, owned face with an uncovered mouth (`_accept_robot_emotion`).
  - `public()` exposes `target_box` so the robot knows which face to score. The device API no longer requires `EmotionService` to start a session.

### Reachy check-in conversations (demo, Oct 2026)
- **Consent gate.** Check-ins need all four scopes `robot_microphone`, `cloud_voice`, `conversation_analysis` and `safety_alerts` (`reachy_tasks.checkin_allowed`). The task payload's `checkin` flag carries this to the robot, and every `/api/device/conversations*` call re-checks it (403 `checkin_consent_required`). In the UI, the Reachy card's "Daily check-ins" switch grants or withdraws them.
- **Flow.**
  - The robot turns speech into text on the robot (Whisper Base via faster-whisper, `voice.py` in "chat" mode).
  - `POST /api/device/conversations` → `/{id}/turn` → `/{id}/end` sends text only.
  - The server calls the reply job's main model chosen on the AI connections card (`services/conversation.py`; first seeded from `LLM_MODEL`, default `google/gemini-2.5-flash-lite`) and returns `reply` (Traditional) plus `speech_text` (Simplified, via `zhconv`, for the robot's Matcha voice).
- **When the model is unavailable:** no key, a 429, or an empty answer gives a fixed reply, so the demo never stalls.
- **Safety: three layers**, because each one alone has missed real risk. On 2 Oct, 「我想自残」 raised no alert: the speech-to-text writes Simplified, and the keyword list had no 自殘.
  1. **Keywords.** `conversation.screen()` runs before any LLM call, on text converted to Traditional with spaces and punctuation stripped. `RISK_WORDS` are plain phrases; `RISK_PATTERNS` add guards (`不想活` but not `不想活動`), the speech-to-text sound-alikes, and the verb a word needs (`喝農藥`, not `噴農藥`). `NOT_RISK` removes everyday phrases (`想死你了`, `我還不想死`, `跳樓大拍賣`), each only within the words between two punctuation marks, so `我想死，你不要管我` still matches. During an OpenRouter outage this list is the **only** check that runs, so it must catch explicit statements by itself; but a match alerts family and ends the chat, and the check-in starts right after a dose, so entries must be unambiguous (`我把早上的藥全部吃了` and `一次吃了五顆` are everyday news; counts are left to the model). A matched turn never reaches the reply or risk-check model, and a flagged conversation gets no post-chat model call (summary NULL, mood `unknown`).
  2. **The model.** `conversation.classify_risk()` judges every other turn: one short call to the `safety` job's model (`RISK_PROMPT`, label `SELF_HARM` / `OVERDOSE` / `NONE`, 4 s deadline). It runs *alongside* the reply, so a turn waits for the slower of the two, not both. Goodbye and turn-limit turns, which get a fixed line, are judged too. `parse_risk` reads a negated label (`No SELF_HARM`, `SELF_HARM: no`) as not understood. A failed or timed-out judgement (`risk_result: "unknown"`, never a risk) is retried in the background with 30 s (`api_device._late_risk_check`), 20 s later when the first try got a 429. A risk it finds flags the turn and alerts, and the conversation's next turn gets the help line without calling the model (`risk_flag` is already set). A retry that fails too is logged as an ERROR. The retry lives only in memory; after a restart, the summary is what remains. Post-chat work waits (bounded) for a conversation's retries still in flight, so a late flag also means no post-chat model call.
  3. **The summary.** `SUMMARY_PROMPT` asks for a third line, `RISK: none|self_harm|overdose` (read with a full-width colon, bold or quotes too; an answer without it goes to the fallback model). With memory on, the combined `AFTER_CHAT_PROMPT` carries the same line (see Check-in memory). Post-chat work has one owner, `services/after_chat.py`, run from `/end` and from the 5-minute after-chat sweep (`jobs/after_chat_job.py`), up to 3 attempts per conversation. When it summarises a conversation that is not yet flagged, a risk alerts family quoting the summary sentence (unless Reachy had memory notes in that chat, see Check-in memory), and the alert says it comes from the summary. If saving the summary fails, the alert is sent on its own. An attempt that gets no RISK judgement (no model answered, or none wrote a RISK line) saves nothing, mood stays NULL, and the sweep tries again (it also catches post-chat work a restart lost). A rate limit leaves the chat `pending` without using up an attempt, but only for its first 10 minutes, so under a lasting rate limit family hear within about half an hour. After the last attempt without a judgement, an unflagged conversation gets a `safety_check_incomplete` family notification in the app (any summary that attempt had is kept). So does one whose last attempt never finished or could not save its results: each claim sets the chat `pending` until the attempt writes its state, the sweep picks up `pending` chats at any attempt count, and `after_chat` ends them without another model call. A conversation still unfinished 2 days after it ended is ended the same way by the sweep (`after_chat.end_stale`).

  A risk from layer 1 or 2 means a fixed help-line reply (119 / 1925), the end of the conversation, and a `flagged` turn. All three layers alert through `conversation.alert_family()`: a `safety_alert` to *every* verified contact (`contact_flag=None`), or a `safety_alert_undelivered` notification when there is none. It sets `risk_flag` with `... AND NOT risk_flag RETURNING`, so a conversation alerts **once**, whichever layers fire. Alerts don't repeat yet, although the robot notice §6 promises that they do. **Release gate:** before robot app 0.9.0 reaches patients beyond the user's own test, a new robot notice version must say that the camera stays on during a check-in (analysed in memory, never saved) and that the chat lasts until goodbye or until Reachy rests; the user decides the notice text (the Reachy card's check-in help already says so). Notice §3 already lists the LLM service for "summaries and safety screening".
- **When it happens:** after the last dose of a slot (state `CHECKIN`, then `POST_SLOT_OBSERVE`), or as a conversation-only task (`reason='checkin'`, no doses; `POST /api/reachy/checkin`, the "Talk to Reachy now" button).
- **How it ends (robot app 0.9.0, the companion session):** a check-in is a companion session: Reachy stays until the patient says goodbye. Spec: `docs/superpowers/specs/2026-10-12-companion-session-design.md`. Today's text chat and the live chat (see "Live voice check-ins" below) follow the same rules in `bridge/session.py`; only the "brain" differs.
  - **Endings:** a goodbye (a `GOODBYES` word, such as 拜拜 or 再見), a risk, a stop (`stop_all`; the microphone consent withdrawn, which today's chat also obeys at once: it ends its conversation as `stopped` with the outcome `microphone_withdrawn`, and its listener stops at the same tick; or in the live chat the access re-check), the rest rule, or a medicine that falls due. Silence alone never ends it (`CHECKIN_SILENCE = None`, since 0.7.1; a number of seconds there brings the silence ending back), and there is no time limit any more.
  - **The camera stays on.** The camera's monitor session (`observe` mode) stays open for the whole session instead of ending before the chat: a check-in task keeps its search session (`MonitorSession.checkin_search`), and after a dose a new observe session starts. Frames go at `COMPANION_CAPTURE_FPS = 2.0` a second (`MonitorStream.set_max_fps`) to save the robot's and the server's CPU. A session that is lost or does not open is tried again; a camera that won't open never ends the chat, but a device that is no longer authorised (`NotAuthorised`) stops the robot, as everywhere else. The robot keeps the time of the server's last answer that said verified (`seen_at`, when that answer came: `MonitorStream.latest_at`), never a later tick's time, so a camera that stopped never keeps Reachy awake. The live relay's camera-first check reads the same session. A live chat whose camera has been unusable (no camera session, or the camera's state not `ok`) for `CAMERA_LOST_SECONDS = 30.0` goes on as today's chat in a new conversation (`CAMERA_FAILED`; the server ends its side as `stopped`), as when its voice detector stops: GPT-Live could never start again. The patient merely out of view never does that. Hand-to-mouth moments the camera sees during the chat, including the chat's last line, are never sent to family (a drink is no news, and the detector is not calibrated at 2 frames a second).
  - **What the server is told.** The companion's observe session starts with `companion` true (`/api/device/monitor/start`), so it uses the check-in face rule (OpenVINO alone, `monitor_service.openvino_only`) even after a dose, where the strict dose rule would not find the patient from across the room. A check-in task's search session, which goes on through the chat, carries no flag: it already uses that rule by its task's reason. The heartbeat carries `companion` too while a session runs: the server then keeps the held in-progress task from expiring (`reachy_tasks.extend_for_companion`, `COMPANION_TASK_EXTEND_SECONDS = 600` past each heartbeat).
  - **Rest:** when for `REST_AFTER_SECONDS = 600.0` there was neither patient speech nor a verified sighting (counted from the latest of the chat's start, the last speech and the last sighting), Reachy says its `REST_LINE` (「我先休息一下，有需要再叫我喔。」) and ends the chat as `patient_left`. While the patient is in view, Reachy stays awake. Patient speech is what the speech listener hears in the text chat (`heard_pause`, `hears_speech`) and `LiveChat.last_speech_at` in the live chat.
  - **Medicine first:** the heartbeat answer has `task_due` (`reachy_tasks.task_due`, read after the heartbeat's write transaction; if that read fails, the answer is false): true when a queued task of this patient's that holds a dose still to take would be leased now by the lease's own rules (its doses startable, `dose_safety.startable_sql`), and also when a missed-dose retry came for the slot of the task the robot holds (a dose left pending before the chat): `enqueue_reachy_task` marks that in-progress task `retry_due` (in its `detail`: the retry's doses and expiry), `task_due` answers true while one of those doses is open and startable and the retry has not expired, and when the task ends (`set_status`) the retry is queued at once for the doses still open. A queued check-in is no medicine and waits for the chat to end, and the lease takes every medicine task before a queued check-in. The runner (`heartbeat_once`) then calls `SlotSession.medicine_due()`: once the patient's words are with the server (today's chat: the listener neither hears nor holds any, and a turn taken is sent and answered first; the live chat: the patient has not been speaking for `MEDICINE_SPEECH_GAP_SECONDS = 2.0`, by the voice detector's state, `LiveChat.last_voice_at`), at most `MEDICINE_WAIT_SECONDS = 30.0` after it, and after the line Reachy is saying, it says its `MEDICINE_LINE` (「該吃藥囉，我們等一下再聊。」), ends the chat as `medicine`, goes to sleep at once (no wind-down clip: it has just said why), and the runner leases the medicine task next. A dose task still running when `task_due` comes finishes first.
  - **The text chat:** the robot opens it with `companion` true (`app_client.conversation_start`), the server keeps that in `conversation.companion`, and the 6-turn limit (`MAX_PATIENT_TURNS`) then no longer closes it: on the server's side only a goodbye or a risk ends it, and the robot ends it for rest, medicine or a stop. `/api/device/conversations/{id}/end` accepts the reason `medicine` (rest uses `patient_left`).

Without a loaded snapshot (the unit tests) the `.env` setup is used. - **Thinking level per job** (Oct 2026; spec `docs/superpowers/specs/2026-10-11-robot-camera-identity-thinking-design.md`). Each job has a level: `off` (the default), `low`, `medium` or `high` (`ai_job.thinking`; the job row's "Thinking" select on the card; `PUT /api/ai/jobs` takes `thinking` per job, and anything else is a 422). `off` sends exactly the request from before (the profile's `reasoning_off` included), so nothing changes until someone picks a level.
  - **What a model can do** is found by Test and saved in its profile as `thinking: {param, levels, ms, always, temperature}`. The probes run in `ai_profile.detect_thinking`, apart from the base test, so a probe that fails or times out never costs the model its base profile. OpenAI-style connections: one request with an invalid `reasoning_effort` whose 400 lists "Supported values are: ...", else one probe per level; a model that refuses `reasoning_effort` altogether can't think. OpenRouter: the model's public `GET {base_url}/models` entry (`reasoning.supported_efforts`, `mandatory`). Each listed level then gets one timed probe (`ms`); a level that comes back empty or cut off is not offered. So Test costs a few more calls and seconds. A profile without `thinking` (an older Test, the seeded models too) is sent no level, like a model that can't think, but the card says "Not checked yet: press Test" (「尚未檢查：請按「測試」」), not "Can't think".

OpenRouter gets `reasoning: {"effort": <level>, "exclude": true}`, plus `temperature` only when the model's entry lists it (`thinking.temperature`). Memory extraction's `temperature=0` is dropped too when thinking is on.

  - **Measuring:** each attempt's metrics add `reasoning_tokens` (from `usage.completion_tokens_details`) and `level`. ### Check-in memory (Oct 2026)
Plan: `docs/superpowers/plans/2026-10-03-reachy-conversation-memory.md`.
- **Consent.** Its own legal kind `memory` (`app/legal/memory/<version>/`), scope `conversation_memory`, off by default. The robot notice and `TERMS_VERSION` were not changed for it; every future `TERMS_VERSION` needs a memory notice too (and a video notice), because `load_documents()` loads every kind. Memory is on only when `core`, `cloud_voice`, `conversation_analysis` and `conversation_memory` are all current (`memory.MEMORY_SCOPES`). It is not in `CHECKIN_SCOPES`. Withdrawing it deletes no notes on the server (memory notice §5); the UI offers the delete through `DELETE /api/memory`.
- **Data.** `patient_memory`: one row per fact per conversation (UUID ids, never reissued after a restore); the newest row per `(kind, subject)` wins, and a patient-entered row (`source='patient'`) beats any chat row. Kinds: `name` (patient entry only, never from speech), `person`, `like`, `routine`, `event` (needs `event_date`). No health, medicine or care facts, for anyone. `patient_memory_deleted` tombstones block re-learning for 7 days. The daily retention job deletes event notes 30 days after their date and tombstones after 7 days.
- **Write path** (`services/after_chat.py`, from `/end` and the 5-minute after-chat sweep `jobs/after_chat_job.py`): one model call (`AFTER_CHAT_PROMPT`) writes the summary, the mood, the `RISK:` line and the facts. A chat without memory consent, or too short (fewer than 2 patient turns or 15 characters), gets the plain `SUMMARY_PROMPT` call instead, so the RISK backstop (safety layer 3) runs for every unflagged chat, memory on or off.
  - Facts are stored only from an answer with an explicit `RISK: none`. An answer without a RISK line is no judgement: nothing is saved and the sweep retries; the last attempt keeps its summary (never facts) and sends `safety_check_incomplete`. `parse_summary` and `risk_line` read the same RISK line, skipping the format echoed back (`RISK: none|self_harm|overdose`).
  - A summary risk alerts family **without the summary quote** whenever Reachy may have had memory notes in that chat, whichever prompt wrote the summary (memory notice §3: family never see the notes): memory on now, or its consent changed after the chat started, and the patient has any note; or the chat had a follow-up. Reachy's lines (the block, the named opening) can carry notes into a summary even on the short-chat `SUMMARY_PROMPT` path.
  - Facts pass `memory.validate_fact()` (which rejects anything `conversation.screen()` matches, checking the subject with its `_` read as spaces too) and must appear in the patient's own words (`grounded`); they are stored under `memory.lock_user()` (`SELECT … FROM "user" … FOR UPDATE`, the same lock deletes and patient edits take) after an uncached consent re-read, and only while the conversation's `risk_flag` is still unset.
  - Before claiming a conversation, `after_chat` waits (bounded) for its late risk checks still in flight, so a late flag means no post-chat model call.
  - No model call for a risk chat or when check-in analysis consent was withdrawn. A rate limit leaves the chat `pending` for the sweep.
- **Read path.** Every turn rebuilds a facts-only block (`memory.build_block`) sent as a second system message after the reply prompt (`SYSTEM_PROMPT` plus the day's background); no summaries or moods (a visitor may be listening). Only the reply gets it, and only on an unflagged, non-keyword, non-closing turn: the risk check, the summary and family alerts never see it. It is built in a savepoint: if it fails, the reply goes without it and the turn (its words, its risk check) is unaffected. The block's preamble repeats "the rules above still apply" (no medical advice); on 3 Oct both pinned models took the two system messages (HTTP 200, ~1.5-2 s) and still sent a dose question to a doctor or pharmacist. The opening line's name comes from `memory.call_name()`: the patient's own `name` entry while memory is on, else the Reachy card's call name or the registered name (see "Live voice check-ins (Phase 2a, test)"). One past event per chat is chosen at start (`conversation.followup_memory_id`) and marked asked only after a real model reply.
- **Deletion.** Chat deletes cascade to their facts; every patient delete and every withdrawn consent scope writes `deletion_ledger` (kinds `conversation`, `memory`, `consent`), replayed by id + owner (consent: only if the restored grant is older than the withdrawal). `replay_ledger` runs the retention purges before clearing the restore marker.
- **Provider routing** (optional): `OPENROUTER_PROVIDER_ONLY` and `OPENROUTER_DATA_COLLECTION` go into every OpenRouter call (reply, risk check, summary, memory) for both models, so with `OPENROUTER_PROVIDER_ONLY` set, every model in use on an OpenRouter connection must be served by those providers. Left unset on the laptop: untested, they can make the fallback unroutable or exclude the free endpoints.

### Live voice check-ins (Phase 2a, test)
Spec: `docs/superpowers/specs/2026-10-12-live-voice-2a-design.md`, and for robot app 0.9.0 `docs/superpowers/specs/2026-10-12-companion-session-design.md` (see **Companion session** below: GPT-Live then runs only while the patient talks). A check-in can be a live voice chat with OpenAI's GPT-Live instead of the turn-by-turn text chat above. **For testing only:** no patient notice or consent covers it yet, so real patients wait for Phase 2b. It is off unless `.env` has `LIVE_VOICE_TEST=1` (`config.LIVE_VOICE_TEST`, read at start), and with `APP_ENV=prod` the app refuses to start while it is on (`dev` only warns). While it is off, no live path is reachable: no card switch or card section, `live` is false in every task payload, and the robot's live WebSocket answers `fallback` with reason `live_disabled`.
- **Why.** A text turn takes 12-14 s, mostly the robot's speech-to-text (Whisper Base, about 9 s). gpt-live-1 listens to a live audio stream and answers in its own voice by itself, over OpenAI's Live WebSocket (`wss://api.openai.com/v1/live/sessions`). It can't write text replies (Test gives `not_chat_model`), so it has a path of its own. It costs about US$0.05 per minute of chat; a muted session with no audio sent is not billed.
- **The relay.** The robot never talks to OpenAI and never sees the key. Robot app 0.8.0 and later opens a WebSocket to `/api/device/conversations/live` with its robot key; the server's `live_session.LiveRelay` opens a GPT-Live session with `live_client.LiveClient` and passes the audio both ways as binary frames (PCM16, mono, 16 kHz; one rate both ways).
  - JSON messages. Robot to server: `start` first (`{task_id, language, rate, bridge_version}`), `end` when the robot stops, `playing` when Reachy's voice starts, `idle` when it stops, and (0.9.0) `speech` when the robot's voice detector hears the patient begin to speak. Server to robot: `ready` (`{conversation_id}`; for a 0.9.0 robot also `speech_text`, the opening the robot says itself), `flush` (drop all queued audio now), `say` (`{speech_text, reason}`: the robot says it with its own Matcha voice), `fallback` (`{reason, conversation_id}`), `end` (`{reason, risk}`), and for a 0.9.0 robot `paused` (GPT-Live was closed until the patient speaks again) and `not_seen` (a `speech` was ignored because the camera has not recognised the patient recently).
  - The WebSocket exists only on the device port (the port rule above). `device_auth.get_device_ws` checks the robot key like `get_device` (lookup, revoked, consent): a bad or revoked key closes the socket with `4401`, missing robot consent with `4403`. One live chat per patient: a second connection closes with `4409`. The patient's slot (`api_device._live_chats`, which `reminders.find_relay` reads) is freed once the chat is over and GPT-Live closed (`LiveRelay.on_over`), before the relay waits for a record or a note to family still running, so the next live chat is not refused meanwhile (round 3 of 17 Oct 2026; a reminder that fires then was never lost: a relay whose chat has ended cannot speak, `LiveRelay.can_speak`, so `reminders.fire` hands it to a check-in task).
  - On `start` the server checks, in this order: `LIVE_VOICE_TEST` (reason `live_disabled`), the audio rate (16 kHz), check-in consent (`reachy_tasks.checkin_allowed`), the leased check-in task, the robot still paired (`live_disabled`), a usable live model. The first failure answers `fallback` with no conversation id, before any conversation row exists. GPT-Live must then start within `live_session.CONNECT_TIMEOUT = 8.0` seconds (measured about 1.2 s), else `fallback` with reason `live_unavailable`, whatever went wrong (GPT-Live's own code, such as `live_auth`, goes only to the server's log).
  - For a robot older than 0.9.0, only after GPT-Live has started does the server add the conversation (`conversation.mode` is `live`, the model is the live model id) with Reachy's opening line as its first turn, and send `ready`. GPT-Live gets the opening line as commentary and says it in its own voice. A 0.9.0 robot gets the companion session instead (see **Companion session** below).
  - GPT-Live's instructions: `conversation.reply_prompt` (Reachy's rules and the day's background), live rules (one or two short sentences, at most 30 characters; answer everything itself, no lookups; if asked, it is Reachy, a robot with an AI voice; never bring up medicines, doses or illness itself, and when asked suggest a doctor or pharmacist, as the reply prompt says; when the patient talks about harming themselves, say it is worried and will get help), the memory block (`memory.build_block`) only while memory consent is current, and the call name.
  - **Access is checked again while the chat runs.** Every `live_session.ACCESS_RECHECK_SECONDS = 10.0` seconds the relay reads again what the text chat checks at every call: the robot is not unpaired (`live_session.PAIRED_SQL`), and robot consent and check-in consent are still current. When one is gone, the chat ends at once with reason `access_withdrawn`, so the patient's voice stops going to OpenAI. The reads of one re-check may take `live_session.ACCESS_CHECK_TIMEOUT = 5.0` seconds; the timer never waits for them. A re-check that fails or times out is tried again at the next round, and `live_session.ACCESS_FAILURES_TO_END = 3` failed re-checks in a row end the chat with reason `access_unverified` (it fails closed: a database that stopped answering never leaves the chat unchecked). A re-check that completes resets the count. A risk found at the same moment still wins. A chat that started with memory consent and finds it no longer current at a re-check goes on as today's text chat (`fallback` with reason `memory_withdrawn` and the conversation id), because GPT-Live's instructions carry the memory block and the memory name, while the text chat checks memory consent at every turn; the wrap-up closes GPT-Live.
- **The hold.** The start of every GPT-Live reply waits `HOLD_SECONDS = 0.5` before its first frame goes to the robot; after that its audio flows as it arrives, and more words of the same patient turn never hold it again. A reply starts when its audio turns non-silent (a sample above `ONSET_LEVEL = 120`, the TCU companion's rule). The hold gives the keyword check time to act before anything is heard: in the Phase 2 spike, screening fired 0.80-2.31 s before a reply was audible, but a calm-sounding sentence could get a reply the moment its words arrived. Each Reachy turn stores `hold_ms` and `first_audio_ms`.
- **Safety.** The help line is always said in the robot's own voice, never GPT-Live's: OpenAI's moderation cut GPT-Live off 9 of 9 times.
  1. **Keywords (layer 1).** `conversation.screen()` runs at every new fragment of GPT-Live's transcript of the patient, over the patient's words since their last pause (`TURN_GAP_SECONDS = 1.5`), so a backchannel from GPT-Live such as 「嗯」 doesn't split them. A match holds at once: forwarding stops, and `flush` also clears what the robot has queued. Once no new fragment has come for `CONFIRM_SECONDS = 0.4`, `screen()` runs on those words again (its `NOT_RISK` rules can clear a partial match): still a match blocks the chat; cleared, the held audio goes on (or is dropped if that reply ended meanwhile).
  2. **Blocking** (`LiveRelay.block`, the one path for every layer, once per chat): stop forwarding and send `flush`; the chat ends with reason `risk`, and its wrap-up sends `say` with reason `risk` (the help line in the robot's own voice) first, then mutes and closes GPT-Live, flags the patient's turn(s), alerts family through `conversation.alert_family()` (once per conversation, its existing guard), adds a Reachy turn with `conversation.HELPLINE`, ends the conversation with reason `risk` and sends `end` with `risk` true. A risk outranks an ending or a fallback decided at the same moment, and a block that lands while a keyword hit is still settling also flags those keyword turns when the words still screen as a risk. A risk found after the ending began only flags its turn and alerts family.
  3. **OpenAI ends the session** (a `content_filter` error, or a close with reason `content`; in the spike it did so on 9 of 9 clear self-harm statements, sometimes mid-reply): the server runs `conversation.classify_risk()` on the patient's last turn at once. The text chat takes over (`fallback` with reason `live_ended`) **only when the answer is an explicit `NONE`**; `SELF_HARM`, `OVERDOSE`, no answer, a failed check or anything else blocks.
  4. **The model (layer 2).** Every closed patient turn gets `classify_risk()` in the background, with the same late retry as the text chat when it gets no answer; a risk blocks. It never delays a reply.
  5. **The summary (layer 3)** is unchanged: it reads the stored turns after the chat.
- **Turns.** GPT-Live's transcript fragments are grouped per role. GPT-Live can answer before its transcript of the patient is complete, so its words never close the patient's turn: a patient pause over `TURN_GAP_SECONDS = 1.5`, a group of `MAX_GROUP_CHARS = 2000` characters, or the end of the chat does. The patient's next turn closes Reachy's (the spoken opening once its sound is over), and turns are stored in the order they began. Each closed group is one `conversation_turn` row, and Reachy's text is the transcript of what GPT-Live said. The turn's `metrics` gain a `live` entry: `transcript_ms` and `fragments` for the patient; `first_audio_ms`, `hold_ms` and `cut` (blocked or flushed) for Reachy.
- **Endings.** A goodbye (a `GOODBYES` word) in a closed patient turn, after which GPT-Live may answer once and the chat ends `GOODBYE_GRACE_SECONDS = 3` after that answer's audio; for a robot older than 0.9.0 also `SILENCE_END_SECONDS = 45` without patient speech and `LIVE_MAX_SECONDS = 600`; the robot's `end` (`ROBOT_END_REASONS`; a 0.9.0 robot also sends `patient_left` for its rest rule and `medicine`); a dropped robot connection; `access_withdrawn` or `access_unverified` (the access re-check above); a block. Every ending closes GPT-Live, stores `conversation.live` (`usage_seconds`, `close_reason`, `fallback_reason`, and for a companion session `stretches`), ends the conversation with its reason and starts the after-chat work as `/api/device/conversations/{id}/end` does. The silence ending was an open question until 12 Oct: the text chat has not ended on silence since robot app 0.7.1 (`CHECKIN_SILENCE = None`), and the user chose to pause GPT-Live while the patient is quiet (billing stops) instead of ending the chat. So for a 0.9.0 robot neither `SILENCE_END_SECONDS` nor `LIVE_MAX_SECONDS` ends it (see **Companion session** below).
- **Fallback.** Any failure goes on as today's text chat, and the robot shows nothing new. Before the conversation exists, `fallback` carries no conversation id and the robot starts a text chat (`/api/device/conversations`). After the chat started (a GPT-Live error, `live_ended`, an unexpected close, `memory_withdrawn`, or `error` when the relay itself fails), `fallback` carries the `conversation_id`, and the robot continues it with `/api/device/conversations/{id}/turn`, which reads the stored turns as history. `conversation.mode` stays `live`, `fallback_reason` says why, and `live_patient_turns` (how many patient turns the live part had) makes the text chat's turn limit count from the fallback. When the robot's own connection drops, the server ends the conversation (`disconnected`) and the robot starts a new text chat. Every database call of the running chat (storing turns, the risk checks' reads and writes, the ending or the fallback) is given up on after `live_session.DB_TIMEOUT_SECONDS = 5.0` seconds, into these same paths (a failed handler falls back with `error`), and the wrap-up waits at most twice that for an event or a timer still being handled before it stops them (a check of OpenAI's cut-off stopped then blocks, as a failed check does), so GPT-Live is always closed and the patient's live slot freed. Once a risk was decided, family are alerted even when storing the open turns failed (the alert quotes the words the check found), and a failure after the help line still sends `end` with `risk` true, so the robot never starts a new text chat after it.
- **Companion session (robot app 0.9.0).** A `start` whose `bridge_version` is 0.9.0 or later (`live_session.companion_robot`, `COMPANION_VERSION`) runs the relay as a companion session; any other `start` runs the path above unchanged. GPT-Live then runs only while the patient talks, in *stretches*, all inside the one robot connection. How the session ends on the robot (rest, medicine first, the camera kept on): "How it ends" in the check-in section above.
  - **Paused start.** After the same start checks, the server writes the conversation (`conversation.mode` `live`, `conversation.companion` true) with Reachy's opening as its first turn and sends `ready` with `speech_text` (the opening in the voice's Simplified characters, `conversation.speech_text`), which the robot says in its own voice. GPT-Live is not started: the relay is *paused*. While paused it keeps only the last `live_session.PRE_ROLL_SECONDS = 2.0` of microphone audio and sends nothing to OpenAI, so nothing is billed.
  - **Camera first.** On the robot's `speech` while paused, the relay starts GPT-Live only when the camera recognised the patient within the last `SEEN_RECENT_SECONDS = 15.0` (`live_session.patient_seen_recently`: the patient's robot monitor session in `monitor_service.registry` has a `MonitorSession.confirmed_at` that recent: the last hit that made its status `verified`, two hits in a row, never a first hit still `verifying`). Otherwise it stays paused and answers `not_seen`, so only the identified patient's voice starts a cloud session. A stretch already running is not cut when the patient steps out of view.
  - **Start and restart.** Each new GPT-Live session must start within `CONNECT_TIMEOUT`. Its instructions are the ones above (rules, call name, memory block) plus a companion note: Reachy has already greeted (the opening quoted as data), and the last `live_session.HISTORY_TURNS = 20` stored turns, quoted as transcript data, never as instructions. Then the relay sends the kept pre-roll, then the live microphone, so the patient's first words reach GPT-Live and the safety checks. The kept audio (the pre-roll and what the microphone sent while GPT-Live started) goes at up to twice real time (`live_session.PRE_ROLL_SEND_SPEED = 2.0`), because GPT-Live drops a faster burst: sent at once in the live test of 12 Oct 2026, the patient's first 1-2 s of each stretch were lost. The sends follow one schedule, so a late timer (Windows' 15.6 ms) is made up, by at most `PACE_SLACK_SECONDS` (0.1 s). While GPT-Live starts, the relay keeps at most `live_session.KEPT_MAX_SECONDS` (17 s: the pre-roll, `DB_TIMEOUT_SECONDS`, `CONNECT_TIMEOUT` and 2 s) of audio; more is dropped oldest first (one WARNING) instead of growing the server's memory. While the kept audio goes out, a robot whose audio since the speech signal that started the stretch (sent on the audio's own socket, in order) runs more than `CATCH_UP_MARGIN_SECONDS` (2 s) ahead of the clock sends faster than real time: what is left is dropped (WARNING), so a robot sending at twice real time or faster can't keep a stretch starting, where no pause rule applies and GPT-Live stays billed. It judges the audio that came, never how long sending took, so a stalled send never costs a real-time robot's words. A start that fails is a `fallback` with reason `live_unavailable` and the conversation id: the text chat goes on in the same conversation. When the patient's words that started it were kept (the pre-roll), nothing has transcribed, screened or stored them, so the robot first gets a `say` with reason `repeat` (`live_session.REPEAT_LINES`: 「不好意思，我剛剛沒聽清楚，可以再說一次嗎？」) and the patient says them again to the text chat's listener.
  - **Pause.** After `QUIET_PAUSE_SECONDS = 30.0` without patient speech (no fragment of the patient's transcript and no `speech` from the robot) once GPT-Live's sound has ended, the relay pauses, but not while a `record_medication_taken`, `notify_family` or `emergency_alert` call still runs (`ToolRegistry.finishing`) or a step of the medication workflow runs (`tool_registry.MEDICATION_TOOLS`, which `agent_bridge` imports: `verify_medication`'s OCR takes up to 36 s, and a watch's `get_pill_intake_result` is asked again and again; `ToolRegistry.checking`, each at most its own `TIMEOUTS` entry from its start; round 3 of 17 Oct 2026: before, 30 s of quiet during a label check closed GPT-Live before it asked for `record_medication_taken`), nor for `INTENT_WAIT_SECONDS` (6 s) after one ended (`ToolRegistry.finished_at`, on the relay's clock; `LiveRelay._tool_answer_due`): the call has just sent GPT-Live its result, and GPT-Live's spoken answer (that family were asked, the applause) or its next step cannot start at once. Once that answer's sound starts, the pause waits for it to end, as for any of GPT-Live's sound; with no answer within the 6 s, the pause comes then. A stretch that is `STRETCH_MAX_SECONDS = 600.0` old pauses at the patient's next turn gap (nobody is talking, GPT-Live is silent and owes no answer to their last words, and no call runs that holds the quiet pause, `_tool_answer_due`; round 4: after 10 minutes of talk it could close GPT-Live during `verify_medication` or a watch's polling), and `STRETCH_HARD_MAX_SECONDS` (60 s later) pauses it anyway, with a `flush` if GPT-Live was speaking. Every pause closes GPT-Live (its usage added up), then handles what it still sent (the event its events loop held and the queued ones: the patient's words are screened and stored, OpenAI's cut-offs are judged; a robot `end` meanwhile lets this finish), then stores the open turns and sends `paused`. The patient's next words (with a recent sighting) start a new stretch; after a pause at the hard limit with recent speech, the next stretch is asked for at once, still camera first.
  - **Endings while a stretch runs.** An ending or a fallback (the robot's `end` for medicine, rest or a stop, a dropped robot, the access re-check) first closes GPT-Live and handles what it still sent, as a pause does, before the open turns are stored: a risk in the patient's last words then takes the risk path (stored, judged, flagged, family alerted; the help line goes to the robot only if it is still there). The access re-check also reads `ended_at` (`live_session.CONVERSATION_ENDED_SQL`): when another writer (the after-chat sweep) ended the conversation, the chat ends at once as `stopped`, as the text chat's 409 does.
  - **Unchanged:** everything above while a stretch runs (the hold, screening, `block`, OpenAI's cut-offs, layer 2, the turns, the goodbye). The access re-check also runs while paused. After a risk (`_risk`) nothing restarts. `conversation.live` counts `stretches` (how many times GPT-Live started), and its `usage_seconds` is the sum over them.

### Startup after a laptop reboot (14 Oct 2026)
- **What actually broke after a full shutdown and power-on** (traced from the Windows event log, Docker Desktop's host logs, the robot's journal and the database on 14 Oct 2026): (1) **Docker Desktop never starts by itself**: `%APPDATA%\Docker\settings-store.json` has `AutoStart: false`, its Run entry is disabled in Task Manager's Startup tab, there is no Docker Windows service and no scheduled task, so nothing listens until someone logs in and launches it (11:35–13:43 that day: 2 h with no server; doses were judged missed hours late, reminders over 15 min late expire). (2) **The device port binds a stale IP**: the laptop's Wi-Fi IPv4 is DHCP and changes between networks (7 addresses in 13 days; the 192.168.137.x network is a Mobile Hotspot hosted by another PC, "IDEAPADGAMING3- 4607"); `docker-compose.yml` maps `${DEVICE_BIND}:8001:8001` and the container keeps that binding from its creation, so after a reboot the engine restarts the app with the old IP, Docker's port forwarder retries for about 60 s and gives up (`bind: cannot assign requested address` in `%LOCALAPPDATA%\Docker\log\host\com.docker.backend.exe.log`), and the container stays "healthy" (the healthcheck hits `/health` inside the container) with no host port 8001: the robot gets `ConnectTimeout` and family get a `robot_offline` LINE notice. Editing `.env` needs a recreate (`docker compose up -d app`), not a restart. (3) **The robot app never auto-starts**: daemon 1.8.3 has no startup-app mechanism (`GET /api/apps/startup-app` is 404); the app ran only after a click in the Reachy Mini Control app, 8.7 min after boot, and a daemon restart kills it too. (4) **The robot's `app_url` is the laptop's old IP** after a network change, polled forever with 10 s timeouts while its status page kept saying "Waiting for a medication reminder from the server". (5) **The LINE tunnel is never restarted** (profile containers stopped since 4 Oct; `scripts/line-tunnel.ps1` must be rerun by hand and gets a new address each time). Latent: the app crashed into a restart if postgres was still in crash recovery when the engine restarted both (no ordering, no retry); the firewall's only inbound rules for the Docker backend are Public-profile-only (a network classified Private blocks 8001); the disconnected Ethernet adapter holds a leftover static 192.168.137.1/24 (ICS residue) that would hijack the robot's subnet if a cable were plugged in; `/tmp` caches (voice clips, dose videos) were wiped by every recreate; a live Check cleared by saving the AI card's live section silently turned check-ins into text chats, with no log line.
- **Fixes.** The server: `app/startup_report.py` logs one `[STARTUP] <stage>: OK ...` or `FAILED: <reason>` line per stage (environment with switches and which secrets are set, never values; database; AI jobs; GPT-Live with the exact reason it is off; models; scheduler jobs; outbox; LINE and its public link; reminders re-armed; the device API; api.openai.com and api.line.me reachability; clock skew against their Date header) and `GET /health` carries the same report as `startup`; `app/database.py` retries postgres for two minutes (`CONNECT_ATTEMPTS`, `CONNECT_RETRY_SECONDS`) instead of crashing; `app/serve.py` exits non-zero when the lifespan failed; when the live model has a key but no passing Check, a Check runs at startup (retried over about a minute) and is saved as the card's button saves it (`startup_report.auto_check_live`); voice clips and dose videos live on named volumes (`medclips`, `dosevideos`). The host: `scripts/medcare-boot.ps1` (at sign-in through a shortcut in the user's Startup folder, because `schtasks` refuses a logon task without admin rights, and every 5 minutes with `-Reconcile` as the scheduled task "MedCare Reachy reconcile", which also starts Docker when it is down; both registered by `scripts/install-autostart.ps1`; log in `logs/startup-<date>.log`; verified on 16 Oct 2026 against the real dead state left by the 14 Oct reboot: Docker from dead to engine in 32 s, stack, ports, tunnel and robot all OK in 76 s) waits for the network, starts Docker Desktop if it is down and waits for the engine, rewrites `DEVICE_BIND` to the current LAN IP and recreates the app when it changed, verifies the host port is really bound and `/health` answers, restarts the LINE tunnel, finds the robot (`REACHY_ROBOT_HOST`, `reachy-mini.local`, else the ARP entry for `REACHY_ROBOT_MAC`), starts its app through the daemon when it is not running and sets its `app_url` when it differs (only while the robot is idle). The robot (app 0.15.0): the runner tracks server reachability, logs `[STARTUP]` lines with the real reason, the status page says "Cannot reach the server at ... for N s" instead of waiting, and `tools/robot-autostart/` installs a systemd timer that starts the app whenever it is not running. Docker Desktop still needs a signed-in user (enable "Start Docker Desktop when you sign in", and Windows auto sign-in if the laptop may reboot unattended).

### Live time, web search and real reminders (14 Oct 2026)

### Emotion during medication (Oct 2026)
- **What is scored.** Every dose session scores the 7 FER classes (`emotion_service.LABELS`) on the verified owned face. This includes moments when the mouth is covered, which are marked `occluded`: synthetic tests showed covered faces shift results toward surprise and angry. Robot server-vision sessions score 4 times a second once the patient is verified; identity checks stay at most 2 Hz.
- **One result per dose session.** `services/dose_emotion.py` writes one `dose_emotion` row per dose session, whatever the outcome: camera commit, confirmation request to family, patient claim, or left unresolved.
  - **What the result uses:** uncovered faces from `PRE_SECONDS` (5 s) before the intake event and `POST_SECONDS` (5 s) after it. Without an event it uses the last 120 s.
  - **"Unsure":** a result with fewer than 4 clear frames, or whose top class scores below `MIN_RELIABLE_SCORE` (0.4), is marked unsure.
  - **Consent:** core consent is re-checked before writing, plus robot camera consent for robot sessions.
  - **Idle sessions:** they are ended after `IDLE_SESSION_SECONDS` (10 min) by the minute job.
- **Unchanged:** the commit path's `during_ingestion` emotion row and `monitor_event.emotion_probabilities` still use uncovered faces since the intake started. That row is what the existing family emotion-alert job reads.
- **Where it shows.** `/api/emotion/medication` and `/api/emotion/medication/{intk_id}`. The `dose_emotion` field on `/api/medications/today` and on `/api/history/intakes` rows feeds the chip on Today, Schedule and History. The chip appears only for doses that were taken or are waiting for family, and shows "mouth covered" or "unsure" as visible text.
- **Not shared with family.** No LINE message carries it. The core notice §4 covers storing it ("facial-expression analysis results at medication time").
- **Still open:** a patient-side delete of per-dose results (core §7). Robots doing their own vision (`vision_on_server=false`) still skip covered mouths and score at 2 Hz.

### Dose videos for family (Oct 2026)
- **Opt-in.** Consent kind `video`, scope `dose_video`, notice `app/legal/video/2026-10/`. The Family page's "Dose videos for family" card shows the notice before switching on. It is the one exception to "camera images are never saved".
- **Capture.** While a monitor session of a consenting patient runs (`MonitorSession.clip_enabled`, checked at start), the JPEGs the server already receives (browser `/vision`, robot `/monitor/frame` and `/monitor/vision`) are also kept in memory for 20 s, at most 10 fps (`services/dose_video.py`). `commit_monitored` (any recorded dose) and the robot's `/tasks/{id}/confirmation` call `capture()`, which encodes the frames before that moment into H.264 with PyAV (`requirements-video.txt`, its own Docker layer) under `DOSE_VIDEO_DIR`.
- **With a confirmation request.** A clip of a dose sent to caregivers (`/tasks/{id}/confirmation`: degraded, uncertain, patient claim) goes out as soon as it is encoded, right after the request, whatever the frame rate (`dose_video.send_with_confirmation`). The request text also gives the AI's estimate (`services/dose_report.py`: `48%（不確定）`, or "not determined" when the camera saw nothing).
- **The request says where its video is** (16 Oct 2026). Before a request is made, `dose_video.clip_outlook` knows whether a clip can come: the dose-video consent current and at least `MIN_FRAMES` fresh frames buffered (taken then, and handed to `capture(frames=...)` once the request exists). The request's evidence carries `video`, on the GPT-Live agent's path (`record_medication_taken`) and the robot's own `/tasks/{id}/confirmation` alike, and `_request_messages` gives its line in both languages: `with_request` (「影片會在下一則訊息送出」, the video follows in the next message), `sent_earlier` (the agent's review message carried it), `none:no_consent` ("Dose videos for family" is off for this patient) or `none:no_frames` (the camera had no recent frames). A `none:no_frames` answer is a lost video and logs one WARNING with the patient id and the frames found (`dose video for patient <id>: no video with the confirmation request: <n> recent frames buffered, 5 needed`); `none:no_consent` is the patient's choice and logs nothing. The reminder an hour later points back to the earlier messages instead. A consent that cannot be read never fails a request: the buffered frames decide, and `_store` reads the consent again before writing. The read gets `dose_video.CONSENT_READ_SECONDS` (5 s, about `DB_TIMEOUT_SECONDS`), and a timeout counts as unreadable, so a slow database never times the record out and loses its request. A clip kept unsent for lack of a public link still counts as `with_request`: the dose_videos job sends it once a link answers (see Late sending), and its WARNING names it.
- **Sending.** `taken_confirmation_job` now goes through the outbox. Each dose line says how it was recorded and the AI's estimate (detector band → `82%（高）` etc., or "not determined" when the camera saw nothing), plus a footnote that the AI can't see the pill. Each clip goes as a separate `dose_video` outbox row, so a rejected video never blocks the text. Every recipient gets their own link, `/api/media/line/<43-char token>.mp4|.jpg` (only the token's SHA-256 is stored). The link is public (no login) and served with Range support by `api_dose_video.py`. The base URL is `PUBLIC_BASE_URL` (taken as set, when it is https), or else the LINE webhook's host when it reaches **this** server.
- **The public link must reach this server** (16 Oct 2026). Two computers share one LINE bot, whose one webhook address leads to whichever ran `scripts/line-tunnel.ps1` last, and the old probe accepted any answer below 500 (the LINE proxy answers 404 itself), so every link went to the other computer's server, which has no such clip. Now each process makes a probe token at import (`dose_video.PROBE_TOKEN`, `secrets.token_urlsafe(32)`: the shape of a real link token, so the proxy forwards it like a family member's video; never stored or logged), `GET /api/media/line/<probe token>.jpg` answers 200 with `PROBE_MARKER` and `Cache-Control: no-store` (any other unknown token is still a 404), and `public_base_url()` accepts the webhook's host only for that 200 with the marker. Otherwise there is no public link, for a reason (`public_link()` returns the base or the reason that went with that very answer, so a check made meanwhile never makes a WARNING say `(None)`): `no LINE token`, `LINE webhook endpoint error` (also a malformed webhook address or an answer that is no JSON object), `tunnel not answering` (a 5xx, such as Cloudflare's 530 for a restarted tunnel, or no answer) or `tunnel reaches another server` (a 404 or any other answer), plus `PUBLIC_BASE_URL is not https`. One WARNING when the reason changes (an INFO when the link answers again), never on every check; the cache times are unchanged (a link 5 min, no link 1 min). The `[STARTUP]` line stage (with the hint that `scripts/line-tunnel.ps1` points LINE's webhook at this server only for `tunnel reaches another server` and `tunnel not answering`) and every lost or late clip's WARNING name the reason: `dose video <id> for intakes <ids> kept unsent: no public link (<reason>)` (`_store`), `... deleted: no public link (<reason>)` (`taken_confirmation_job`), and the dose event's line.
- **Late sending.** The `dose_videos` job (`dose_video.maintain`, every 2 min) runs the deletions below, then `retry_unsent`: a clip not sent, not deleted, younger than 4 h, goes out with `send_with_confirmation` once a public link answers, but only with the request it was made for (`dose_video.OWN_REQUEST_SQL`: the newest request of its doses made before the clip, since `capture` runs once the request exists) and only while that request is still open (`resolution IS NULL`). The clip row is locked and checked again (`SELECT ... FOR UPDATE`: another worker may have sent or deleted it meanwhile), sending marks it sent, and the outbox's dedupe key stops a second message. A clip whose request was answered or expired is left to the deletion rules, even when a newer request for the same dose is open (round 3 of 17 Oct 2026: family got the older footage under the new request).
- **Deletion.** The cleanup runs every 2 min. Files go 10 min after every recipient's app fetched the last byte or LINE sent `videoPlayComplete` (`trackingId` `dv-<link uuid hex>`); after 24 h in any case; at once on withdrawal (`api_consent` calls `delete_all`); and when never sent within 4 h, with no recipients, or with no public link. A clip never sent within 4 h is a lost video: one WARNING each, `dose video <id> for intakes <ids> deleted unsent: its family request was closed` or `...: no public link for 4 h` (no token in the line). Rows stay as a record without media. LINE messages can't be recalled, so delivered videos stay on family phones.

### Schedules, stock, adherence (Oct 2026)
- **Schedules** live in `services/schedule.py`. `medication.schedule_time` holds the four preset booleans (08:00, 12:00, 20:00, 22:00), plus optional `custom_times` (`"HH:MM"`, at most 8 times a day in total) and `weekdays` (ISO 1 = Monday … 7 = Sunday; missing means every day). Rows are generated 30 days ahead, or until `use_before`. Nothing tops them up yet, so a schedule simply ends 30 days after its last edit.
- **Stock is `NUMERIC(8,2)`** (half tablets).
  - Every taken dose removes `units_per_dose` through `intake_repository.take_stock`, and stores the amount in `intake.units_taken`.
  - Undo calls `return_stock` with that stored amount. Rows taken before the column existed restore 1.
  - Don't write `pills_remaining-1` anywhere.
  - Refills go through `POST /api/medications/{id}/supply`, which logs them in `medication_supply`.
  - The refill alert fires at ≤7 **days** of supply (`schedule.supply`).
- **Overdose protection (「防止重複服藥」): per patient, on by default.** (On 3 Oct, test alerts at midnight recorded the 08:00, 12:00 and 20:00 doses within an hour.) The switch is `notification_settings.overdose_protection`, the field `overdose_protection` of `GET`/`POST`/`PUT /api/notify/settings` (left out of a save: kept). All four rules live in `services/dose_safety.py`; R1's arithmetic is `schedule.due_from`.
  - **R1, due:** from DOSE_EARLY_MINUTES (120) before its time, but never before halfway from the same medicine's previous dose.
  - **R2, minimum gap** from the same medicine's nearest *taken* dose, by actual intake time:
    - `medication.min_interval_minutes` (30-2880), else half the shortest gap between its daily times (across midnight; once a day: 12 h; allegra at 08/12/20/22: 60 min), else 240 min.
    - It applies to ad-hoc Take Now doses too.
  - **R3, daily maximum:** `medication.max_daily_doses` (1-24), else its number of daily times (unscheduled: no limit).
    - It counts taken doses *scheduled* on the dose's Taipei day (an ad-hoc dose: the day it was taken).
    - So a 22:00 dose taken at 00:30 counts for its own day, not the next.
  - **A dose waiting for family's answer counts as taken** for R2 and R3, at its open request's `created_at` (`FACTS_SQL`'s `last_taken_pending`). Every robot dose goes to family today (10 fps, `degraded`), and up to 2 h without an answer must not leave room for a second pill: Take Now, a tap or the next dose's robot request in that time is refused. Of two requests for one medicine, the earlier one counts against the later one.
  - **R4, expiry:** a dose not taken by halfway to the same medicine's next *scheduled* dose (for the last of a day: the next day's first) stays missed. Take Now then refuses (`dose_expired`) rather than make an ad-hoc dose.
    - **Ad-hoc rows** are told apart by their time: the schedule generates whole minutes, Take Now stores the moment it made the row, never a whole minute (`dose_safety.is_ad_hoc` / `ad_hoc_sql`). An ad-hoc dose never expires, and `next_sql` leaves ad-hoc rows out, so an abandoned or later Take Now moves no dose's halfway point.
  - **Where it is enforced:** `dose_safety.check(conn, u_id, ids, at=, lock=, started_at=, after_intake=)`, under the intake row lock.
    - Every path that starts a dose: robot tasks, monitor starts, the manual task, Take Now (ad-hoc rows included).
    - Every path that records it taken or sends it to family: `commit_monitored`, `transition_intake`, `dose_confirmation.create` / `resolve`, legacy `/medicines`. These pass `lock=True`: `LOCK_SQL` locks the medicines' rows **in a statement of its own, before** `FACTS_SQL` reads. (`FOR UPDATE` inside the reading statement does not work: under READ COMMITTED it keeps the snapshot from before it waited, and two doses of one medicine recorded at once both passed.)
    - **Evidence paths judge R1 and R4 when the camera session started** (`MonitorSession.started_at`; the robot's confirmation uses its open session for that dose): the dose was allowed then, so a pill swallowed a minute after the halfway point is still recorded and spaces the next dose. R2 and R3 are judged when the pill went down.
    - Queries that pick doses use the SQL forms: `startable_sql` (lease, manual task: R1 and R4 under the switch) and `open_sql` (Take Now and the legacy page: which dose a pill counts for). The lease looks only at a task's open doses: a taken dose past its halfway point doesn't hold back the slot.
  - **`FACTS_SQL` and the tests:** `FACTS_SQL` gathers what the rules need, as of the moment judged (`previous_time` leaves out an ad-hoc dose made after it). `tests/dose_facts.py` answers it for the tests' fake databases, so change both together.
  - **Refusal:** a `schedule.DoseRefused` (`DoseNotDueYet`, `dose_safety.DoseTooSoon` / `DailyMaxReached` / `DoseExpired`) → 409 (handler in `main.py`).
    - The body: `{"detail", "intk_id", "med_name", "scheduled_time"}`, plus `due_from` (not due), `last_taken_at`, `next_allowed_at`, `min_interval_minutes` and `last_taken_pending` (too soon), `next_allowed_at`, `taken_today` and `max_daily_doses` (daily maximum, the next Taipei day), or `expired_at`.
    - `reply` is one sentence in the patient's language (`language`: the latest check-in's, else zh-TW); `speech_text` is the same in Simplified for the robot's voice. A medicine named in Chinese is named (the robot can say it); one in Latin letters is 「這個藥」 except in the written daily-maximum sentence.
    - `after_intake` is true on paths with evidence of a pill already swallowed (camera commit, the robot's request, a caregiver's answer). The sentence then says it was not recorded and to tell family if unwell (「這次沒有記錄，因為…」), and that family has been told when a double-dose alert went.
    - The web shows `reply` only when `language` matches the page's language; otherwise its own words (`lib/doses.ts`).
  - **A caregiver's 'taken'** is judged at the request's `created_at`, which is also stored as `actual_intake_time`: the next gap counts from when the pill went down. `taken_confirmation_job` therefore keeps such doses by `GREATEST(actual_intake_time, resolved_at)`.
  - **Double-dose alert:** a `dose_too_soon` / `daily_max_reached` refusal on a path with evidence queues a priority-0 `double_dose_alert` to verified family with `notify_missed`, at most once per dose in a rolling hour (`ALERT_EVERY`: an outbox row for the dose in the last hour holds it).
    - Evidence: a camera commit, any robot confirmation request, a caregiver's 'taken'.
    - A refused button press only shows its sentence.
  - **Reminders (`missed_dose_job`)** judge the slot's doses on the run's clock: the robot is sent for the doses allowed (one medicine's refusal doesn't keep it from the others), inside a savepoint so a late refusal never undoes the reminder flag. The patient's LINE reminder asks only for allowed doses and gives each held-back dose its sentence (e.g. 「…已經錯過了，請不要補吃」), never 「請盡快服用」 for it. Reminder and missed-alert times are in `MEDCARE_TIMEZONE` (until 3 Oct they were UTC: "14:00" for the 22:00 dose).
  - **The legacy page** (`/medicines/{id}/taken`) uses the open dose a pill counts for, else today's nearest open dose, so a refusal says why (with protection off it records as before); `medicines.html` and `dashboard.html` show `reply`.
  - **`taken_notified`** is cleared whenever a dose becomes or stops being 'taken' (`commit_monitored`, `transition_intake`, `resolve`, `undo_monitored`), and the taken report's outbox key names the recording time: a dose taken again is reported again. The report quotes a family confirmation only for a dose recorded that way (`caregiver_confirmed`). (On 3 Oct the test records were reverted to pending/missed with `taken_notified` still TRUE and their 'confirmed' requests left in place.)
  - **LINE confirmation requests** say when the medicine was last recorded (within 24 h) and how early the dose is (over 30 min), with protection on or off.
  - **Off:** nothing is refused and no alert is sent. Turning it off writes a notification and tells every verified family contact on LINE; turning it on again sends nothing.
  - **Medication API:** create, update and list take `min_interval_minutes` and `max_daily_doses` (null = the default; an update that leaves one out keeps it). The list adds `default_min_interval_minutes` and `default_max_daily_doses`, and `/today` rows add `expires_at` (null: never), which the web prefers over its own reckoning. The medication form warns (doesn't block) when a limit refuses some of the medicine's own scheduled doses.
  - **Skip:** skipping a later dose is still allowed.
  - **Which dose a pill counts for:** the open dose nearest to now; the earlier one on a tie.
- **Archive, don't delete.** `POST …/archive` stops a course: future pending rows go, history stays, and the missed-dose job skips inactive medications. `…/reactivate` regenerates from now. `DELETE` returns 409 `has_history` unless the medication never had a past or resolved dose.
- **Adherence** follows one rule (`services/adherence.py`), used by `/api/history/summary` and the weekly LINE summary:
  - Only due doses count. Future doses never do, and a pending dose counts only once it is more than 1 h overdue.
  - Only `taken` is adherent; awaiting confirmation is not, yet.
  - The streak skips days with no doses.
  - `/api/history/intakes` is past-only and paged (`{items, total, has_more}`).
- **Browser auto-record** follows the robot's rule: one `solid_oral` unit, otherwise the person confirms.

### Prescription OCR (repaired 4 Oct 2026; every medicine on the paper)
- **What broke (3-4 Oct):** the code default `OCR_MODEL=gemini-3.8-flash` answered every scan with 503 "high demand", and the old code returned every field as `N/A`, for every account. Then a real three-medicine pharmacy receipt (dot-matrix 藥品明細收據) failed with `ocr_incomplete_schedule`, and the one-medicine prompt returned one medicine with invented fields (a hospital from the address, the prescriber's institution code as the physician, the visit date as use-before).
- **Models:** `gemini-3.5-flash` first, then once `gemini-3.5-flash-lite` (`app/config.py`, `OCR_DEFAULT_MODEL` / `OCR_DEFAULT_FALLBACK_MODEL`; `tests/test_ocr_service.py` pins both and checks `.env.example`). Flash read the receipt more accurately (2 of 3 names exact against 1 of 3; flash-lite gave one row another row's name) but takes 7-12 s against 2-3 s, so `OCR_GEMINI_TIMEOUT` is 25 s. Measurements: `docs/OCR.md`. Don't change a default without a live scan. Neither model is reliable letter by letter on dot-matrix print: the user checks each card.
- **Setup:** only `GEMINI_API_KEY` in `.env`. One process-wide `OCRService` (warmed in lifespan) serves every account; `/api/ocr/parse` checks only core consent.
- **One Gemini request per scan** returns the paper's fields, a `medications` list (one entry per medicine line, copied as printed) and the six schedule icons. 429/5xx, a timeout or a 404 gets one try on the fallback, all within `OCR_GEMINI_IMAGE_BUDGET` (45 s, also the route's limit). Auth errors are not retried. Without a key: Ollama, two passes sharing `OLLAMA_TIMEOUT`.
- **The prompt forbids guessing** (copy printed text, `N/A` for absent labels, no hospital from an address, no code as a person) and explains the receipt labels (就醫序號, 開立處方箋之醫院(診所)/醫師 code, 藥費/藥事費, 調劑者, compact ROC dates). Keep those rules when editing it; `test_the_prompt_explains_receipt_labels_and_forbids_guessing` checks them.
- **The server works out the rest** in `app/services/ocr_parsing.py` (pure, `tests/test_ocr_parsing.py`): dose times from each medicine's usage text (一天N次, 分N次, QD-QID also dotted, Q4H-Q12H, 早晚, 三餐, 睡前, 飯前/飯後, PRN …; 1/day morning, 2 + evening, 3 + noon, 4 + bedtime; 每晚睡前 is one bedtime dose; a range 一天3-4次 is 3 with `max_per_day` 4; QOD is `interval_hours` 48 with no times), ISO dates from ROC forms with plausibility windows, dose form (only tablets and capsules are `solid_oral`; drops, creams, OPH, vaginal forms and unknowns are not), tablets per dose (半 only next to a tablet word: 飯前半小時 is a time) and suggested stock, and name checks (codes, addresses and labels removed from institution names). A readable icon row wins for a paper with one medicine; with several it only fills a medicine without times.
- **No ID numbers or birth dates** leave the server: `strip_identifiers` runs on every text field before it is read and on the whole answer. Its labels need a value of the right shape and English labels whole words: an earlier version turned "Calcium Dobesilate" into "Calcium esilate". `test_medicine_text_is_never_taken_for_an_identifier` guards this; add to it when widening a pattern.
- **Response:** the old 20 fields hold the first medicine plus the paper's fields; `medications`, `pharmacy`, `visit_date` and `document_type` are new. 422 `ocr_incomplete_schedule` only when no medicine has any schedule information (a time, a meal mark, as-needed, or an interval such as QOD).
- **Scan page:** one editable card per medicine with an "add this" box; each kept one goes through `POST /api/medications` with its `dose_form`, `units_per_dose`, `schedule_time` (custom times too), `pills_remaining` and a last day (`use_before` = dispensing date + days − 1, with `course_end` in `prescription_meta` so the Medications page and `/today` don't call it an expiry). A course already ended by the paper starts unticked and can't be saved until its last day changes; `schedule.occurrences` also generates nothing for a `use_before` before today. Less than one dose on hand blocks the save; the stock never falls back to a count of bottles. As-needed cards edit a daily maximum, never dose times. Cards matching an active medicine's name start unticked (checked again before saving). Failed saves show the page's own words, not the server's text. Logic in `frontend_source/src/lib/scan.ts` (`tests/scan.unit.ts`, `tests/scan.spec.ts`).
- **Legacy `/ocr` page:** still one medicine; `/ocr/save` stores its scanned `dose_form` and `units_per_dose` (`other` when missing).
- **Failures are never success-shaped:** non-2xx `{error, code}` (`OCRServiceError`). The Scan page shows `scan.errors.<code>` from `i18n.ts` (en + zh-TW); a new code needs both strings. The key goes only in the `x-goog-api-key` header; logs name the model and status, never the key, photo or text.
- Not yet tested: a real photo through the Scan page camera, and the new code on the running stack (not rebuilt).

### ML services are singletons warmed at startup
`main.py` lifespan calls `get_instance()` on FaceRecognition, Emotion, Line, and IntakeDetection. Endpoints then check the **class attribute** `_available` *without* calling `get_instance()` (e.g. `api_monitor.start` returns 503 if either is False). **If you add a service, warm it in lifespan** or its endpoints will 503 forever.

### DB — asyncpg, no ORM
- Raw SQL only. `schedule_time` and `prescription_meta` are JSONB — `json.dumps()` before passing to asyncpg.
- `"user"` is quoted everywhere (PostgreSQL reserved word).
- Dev runs a **local `postgres:16-alpine` container** (`postgresql://…@postgres:5432/medcareai2`), not Supabase. Production points at Supabase direct (5432), not the pooler (6543). Query latency differs by ~100× between these — re-measure before assuming a DB step is cheap.

### Navigation in React SPA
Use `window.location.href = '/path'` for auth transitions (login, logout, post-registration); React Router `navigate()` only for non-auth changes. Reason: `navigate()` doesn't re-run mount `useEffect`s, so `onboardingComplete` from localStorage goes stale.

### Logout — clear all localStorage flags
`face_auth_session`, `face_auth_token`, `onboarding_complete`, `onboarding_face_done`.

## Dependencies — smaller than you'd expect
`requirements.txt` is 19 lines. The complete installed ML stack is **`openvino`, `onnxruntime`, `opencv-python-headless`** (+ numpy/scipy/pillow). Image size: **1.67GB**.

- **No `torch`** — not installed, not in requirements, not imported anywhere in `app/`. The emotion model is ONNX (MobileNetV3-Large, 4.21M params, 112×112 input).
- **No `mediapipe` server-side** — it's a client npm package (`@mediapipe/tasks-vision`).
- **No `ultralytics`** — lazy-imported only by OCR's optional YOLO page detection, and absent. OCR runs without it: the whole photo goes to Gemini.

The Dockerfile installs `requirements.txt` and nothing else.

## Known Issues
- **Static assets aren't cached.** `serve_spa` (`main.py:101-109`) returns a bare `FileResponse`: no `Cache-Control`, and conditional requests return **200 + full body instead of 304** (verified). `HEAD` returns 405. The MediaPipe assets under `/wasm` and `/models` total **25.6MB** and can be re-downloaded every session — negligible on localhost, ~10s per session on a tablet over WiFi.
- **MediaPipe loads lazily on button press**, and only *after* the camera opens (`Intake.tsx:354`), adding ~0.6s (warm) to ~1.5s (cold) to startup. The three models also load sequentially rather than in parallel (`monitorWorker.ts:23-34`).
- **GPU→CPU delegate fallback re-runs the entire 3-model init** (`monitorWorker.ts:53-57`), doubling init time on hardware without WebGL2.

## Common Gotchas
1. **`face_auth_token` expired?** 8h TTL. Regenerate inside the container:
   `python3 -c "from itsdangerous import URLSafeTimedSerializer; print(URLSafeTimedSerializer('change-me-in-production-32chars!!').dumps({'u_id':1,'name':'Ferdinan'}))"`
2. **asyncpg `expected str, got dict`?** Wrap the dict in `json.dumps()` (JSONB column).
3. **React page shows wrong user?** Supabase and face sessions conflict — clear `sb-*-auth-token` from localStorage when testing face auth.
4. **Models not loading?** Check `/health`. OpenVINO IR files must be at the volume path in `config.py`.
5. **Never measure HTTP transfers with PowerShell `Invoke-WebRequest` (PS 5.1).** It reported 24.5s for assets `curl` fetched in 0.12s — a ~200× overstatement from response buffering. Use `curl` via the Bash tool for any timing work.
